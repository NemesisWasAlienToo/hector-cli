# Torizon OS on Verdin iMX8M Plus in Renode: what needed fixing

Baseline: upstream Renode's FRDM-i.MX8MP Linux example (`scripts/single-node/nxp-imx8mplus_linux.resc`).
This lists what the official Torizon OS image (7.8.0+build.60) uses beyond that example, how each
problem was found, and how it was fixed. Only issues that blocked the boot were fixed; non-fatal probe
failures of unmodeled peripherals (CAAM, SNVS RTC, APBH DMA, VPU, PCIe, audio, PMIC) were left as is.

## Image and boot flow

| # | What Torizon / Verdin needs | How it was found | Fix |
|---|---|---|---|
| 1 | Ships only binaries: `imx-boot` (SPL + DDR fw + FIT{U-Boot, BL31, DTB}), not the ELFs the example loads | Listing the Tezi tarball; `dtc` on the FDT found at 0x58000 in `imx-boot` showed the FIT with `load` addresses | `scripts/fit_extract.py` pulls U-Boot (+ appended control DTB) and BL31 out of the FIT; the resc loads them as binaries and starts cpu0 at BL31 (0x970000). `EnableUbootMode` isn't used (it needs ELF symbols). |
| 2 | Rootfs is an OSTree tarball that Tezi installs into an ext4 partition labelled `otaroot`; boot runs `boot.scr` → `/boot/loader/uEnv.txt` | Tezi `image.json` (partition layout) and the `boot.scr` / `uEnv.txt` inside the rootfs tarball | `prepare-image.sh` rebuilds what Tezi writes: MBR + ext4 `otaroot` (built as root in a container so ownership and hardlinks survive), and boot0 with `imx-boot` at offset 0. No boot files, env or bootargs are changed. |
| 3 | Toradex U-Boot identifies the module from the factory config block (eMMC boot0, last 512 B) | `uboot_config` (`CONFIG_TDX_CFG_BLOCK_*`); without it U-Boot prints `MISSING TORADEX CONFIG BLOCK` | `scripts/tdx_cfgblock.py` writes a valid block. Default product 0061 (Verdin iMX8M Plus Quad 2GB, no Wi-Fi/BT), so U-Boot sets `variant=nonwifi` and Torizon boots `imx8mp-verdin-nonwifi-dev.dtb`. 0063 (4 GB, no Wi-Fi/BT) is available as `toradex-verdin-imx8mp-4gb.repl`. |
| 4 | Module boots from eMMC on uSDHC3, and U-Boot takes its env device from the boot device (`mmc 2`, boot0) | `uboot_config` (`CONFIG_SYS_MMC_ENV_DEV=2`, `ENV_PART=1`) and U-Boot's ROM API boot-device query | ROM API stub reports `BT_DEV_TYPE_MMC`, instance 2 (FRDM's stub reports instance 0). |
| 5 | Board: DDR size, console on UART3 (`ttymxc2`), KSZ9131 PHYs at MDIO address 7, on-module I2C devices | Torizon kernel DTB and U-Boot control DTB decompiled with `dtc` (`stdout-path`, `ethernet-phy@7`, i2c children) | `platforms/boards/toradex-verdin-imx8mp.repl` on top of the upstream SoC repl. |

## Platform models (blocked the boot)

| # | Symptom | How it was found | Fix |
|---|---|---|---|
| 6 | U-Boot: `mmc@30b60000 - probe failed: -10`, `failed to set rate ... error = -1717986921`. Torizon's U-Boot is upstream v2024.07 with the DM clock driver, which derives every rate from ANA_PLL; the SoC repl tagged all of ANA_PLL as `0xFFFFFFFF` (ref-sel = "dummy", bypass on, garbage dividers). The NXP U-Boot of the FRDM example uses legacy clock code. | The version's git hash `3f772959501c` matched upstream tag v2024.07; `drivers/clk/imx/clk-imx8mp.c` / `clk-pll14xx.c` showed which register bits are read. | `platforms/cpus/nxp-mimx8ml.repl`: tags for all PLL GEN_CTRL/FDIV registers with locked, enabled, non-bypassed values and real dividers. |
| 7 | Linux: `CPU1: failed to come online` (with SMP, i.e. without `nosmp`/`maxcpus=1`). NXP TF-A's PSCI CPU_ON powers a core up by clearing and setting `SRC_A53RCR1.A53_COREx_ENABLE`; the SRC model only un-halted the core there and never loaded its PC from the SRC GPRs (RVBAR), so it started at 0. | Verbose debug image (`ignore_loglevel earlycon keep_bootcon` via Torizon's `torizon_bootargs_r`); NXP TF-A `plat/imx/imx8m/gpc_common.c` (`imx_set_cpu_pwr_on`). | `NXP_IMX8MP_SystemResetController`: a 0→1 transition of `A53_COREx_ENABLE` restarts the core at its RVBAR. |
| 8 | Boot hung silently after `Freeing initrd memory` (the reason `cpuidle.off=1` was needed). The DTB's `cpu-pd-wait` idle state (PSCI power-down, `local-timer-stop`) makes TF-A arm the GPC, disable the core's GIC CPU interface and park the core in `wfi`; hardware then powers it down and wakes it through the GIC's wake request. Renode had a flip-flop stub as GPC and only a tag for the system counter that Linux uses as broadcast timer. | Sampling `cpuN PC` every 10 s of virtual time and symbolizing with `nm vmlinux` (KASLR is off: no RNG seed): three cores sat in TF-A (0x976448), one in `tick_check_broadcast_expired`. TF-A `imx8m_psci_common.c` / `gpc_common.c` and Linux `timer-imx-sysctr.c` gave the register-level contract. Noisy logs of the new models then showed wakes working until one race: the broadcast IRQ fired as core0 parked, and the GIC refused to target a sleeping CPU (`IsAffinityRoutingTargetingCPU` returns `!IsSleeping`). | New `Miscellaneous.NXP_IMX8MP_GPC` (core power-down on WFI when armed; wake on the GIC wake request, restarting at the SRC entry; other registers keep the flip-flop behaviour). New `Timers.NXP_IMX_SystemCounter` (CNTCV + compare frame 0, SPI 47). `ARM_GenericInterruptController`: `WakeRequest` event / `IsWakeRequestAsserted`, which, unlike delivery, count interrupts routed to a sleeping CPU. |
| 9 | Board reset by wdog1 (`Watchdog timed out, requesting machine reset`) before systemd took over the watchdog. U-Boot arms it for 60 s; with Renode's default 100 MIPS per core the guest needed ~65 s of virtual time to get there. | Renode log with host/virtual timestamps per UART line; comparing kernel uptime at the same message for two MIPS settings (17.3 s vs 1.45 s at initramfs) gave the instruction count of the boot. | Verdin repl: `PerformanceInMips: 400` (takeover after ~18 s of virtual time). Higher values make busy-waits expensive: polling the system counter runs ~13x slower than regular code in Renode, so at 1200 MIPS U-Boot's 1 s autoboot countdown took ~4 min of wall-clock time. |

| 13 | Emulation aborted after switching to the real root: `cpu3: CPU abort [PC=0x971020]: Unexpected register state in process_interrupt!`. TF-A sets `SCR_EL3.FIQ` (FIQs to EL3) without `SCR_EL3.IRQ` around PSCI suspend; tlib's interrupt routing table only handles SCR_EL3 IRQ/FIQ/EA bits that are all equal (plus one ignore case) and aborts otherwise. | The host CPU went idle mid-boot; the Renode log showed the abort. The PC is inside BL31. The message comes from `tlib/arch/arm64/helper.c` (`establish_interrupts_target_el`), and TF-A's `imx_domain_suspend` is what sets `SCR_FIQ_BIT`. | `tlib/arch/arm64/helper.c`: route each physical FIQ/IRQ by its own SCR_EL3 bit (the table is evaluated with the other routing bits set like it); differently routed pending FIQ+IRQ are tried FIQ first. |
| 14 | `Kernel panic - not syncing: FIQ taken without a root FIQ handler` once userspace runs. NXP's busfreq driver asks TF-A for DDR DVFS when idle; TF-A then raises SGI 8 (Group 0, i.e. FIQ) on the other cores. TF-A only installs its SGI 8 handler (and routes FIQs to EL3, `SCR_EL3.FIQ`) if SPL left a DDR timing table with setpoints at `SAVED_DRAM_TIMING_BASE` (OCRAM_S). SPL doesn't run in Renode, so the table was empty and the FIQ reached Linux. | Temporary logs in tlib (FIQ taken below EL3, with SCR_EL3) and the GIC (FIQ signalled to a non-secure CPU): SGI 8 / Group 0, `SCR_EL3=0x4030731` (FIQ bit clear). TF-A's only Group 0 interrupt is SGI 8 (`plat_imx8_gic.c`), raised in `ddr/dram.c`; `dram_info_init` returns before registering the handler when `fsp_table` is empty. BL31's early read at 0x18004C (OCRAM_S + 76) is `fsp_table[0]`. Linux `busfreq-imx8mq.c` showed how the setpoints are used. | SoC repl: OCRAM_S is RAM (was a tag), initialized like SPL with the boot setpoint `fsp_table[0] = 4000` (LPDDR4-4000). Kept in the SoC repl because the upstream FRDM example hit the same panic once #6 gave Linux sane clocks (its busfreq driver then probes), found by re-running `tests/platforms/frdm-imx8mp_linux.robot`. TF-A's DVFS then parks/releases the cores and touches no DDR controller registers (`dram_type` reads 0 from the tag-only DDRC, and DDR4 switching isn't built in). |
| 15 | With #14 fixed, the boot went silent after the root switch: TF-A's DDR DVFS now runs and, since the tag-only DDR controller reports `MSTR.ddr_type = 0`, executes the DDR4 software frequency change (`IMX8M_DDR4_DVFS` is built in), which spins on `DDRC_DBGCAM` (0x3D400308) and further on `STAT`/`DFISTAT`, whose values must change over the sequence. | Host CPU busy but no console output; the Renode log was flooded with `cpu0: 0x974818 ... ReadDoubleWord ... 0x3D400308` (BL31). TF-A `ddr/ddr4_dvfs.c` (`ddr4_swffc`, `sw_pstate`, `ddr4_mr_write`) gave the handshakes. | New `Miscellaneous.NXP_IMX8MP_DDRC` (SoC repl, 0x3D400000): stores registers; `STAT` follows `PWRCTL.selfref_sw`, `DFISTAT.dfi_init_complete` is the inverse of `DFIMISC.dfi_init_start`, `SWSTAT` follows `SWCTL`, `MRSTAT`/`PSTAT` idle, `DBGCAM` empty. |
| 16 | Emulation aborted in userspace (on any core, also with `maxcpus=1`): `tcg_reg_alloc_op: TCGv 'unnamed' must be in register at this point when allocating arg 1 of 'add_i64'`. Translator bug for AdvSIMD load/store *single structure* (here `st4 {v2.s-v5.s}[0], [x1]` in a libc NEON routine): the per-element stride constant was a plain TCG temp (`tcg_constant_i64` is `tcg_const_i64` in tlib), which dies at the branches the element accesses emit, so advancing the address after the first element failed. | Crash PCs always ended in `...8244` (same library code, ASLR). Temporary dump of the guest words at PC in `TranslationCPU.ReportAbort`, disassembled with `aarch64-linux-gnu-objdump`. A bare Cortex-A53 test of the same words did not reproduce it, so the TCG error was extended to print the guest PC of the instruction being allocated (last `insn_start`), which pointed at the `st4`. | `tlib/arch/arm64/translate-a64.c` `disas_ldst_single_struct`: stride as `tcg_const_local_i64` (as `disas_ldst_multiple_struct` already does), freed after the loop. |

## Renode / tooling (not Torizon)

| # | Symptom | How it was found | Fix |
|---|---|---|---|
| 10 | Renode's memory grew ~30 MB/s until the host ran out; the first uncapped run froze the PC. With stdin redirected and at EOF (headless runs: `< /dev/null`, or `docker run` without `-i`), `ConsoleIOSource.RedirectedHandling` loops on `Console.Read()`, which returns -1 forever, and every -1 is queued in AntShell's `BlockingCollection<int>` input buffer. | Capped container (5 GiB, no swap) plus a host-memory guard. Growth was the same with 4 GiB and 2 GiB of guest RAM. `memory_ddr IsTouched N` showed only 15/128 RAM segments in use. `dotnet-dump analyze -c "dumpheap -stat"` showed 1.25 GB of the heap in `ConcurrentQueueSegment<Int32>` (dotnet-gcdump under-reports large arrays and misled at first). | `src/Infrastructure/src/UI/ConsoleIOSource.cs`: report EOF once, then stop reading. `docker/run.sh` also applies `--memory`/`--cpus` caps and `DOTNET_GCHeapHardLimit`. |
| 17 | With 4 cores the container hit its memory cap (`Killed`) after ~26 s of virtual time, while 1 core fit in 2.5 GiB. Each emulated core has its own translation cache that may grow to 512 MiB (`[translation] max-tb-size`), up to 2 GiB for 4 cores on top of guest RAM. | Single- vs multi-core runs under the same cap; `TranslationCPU.DefaultMaximumTranslationCacheSize`. | `max-tb-size = 67108864` (64 MiB) in Renode's user config (`.docker-home/.config/renode/config` for the docker setup). |
| 11 | The .NET SDK in the build container can't create named mutexes as non-root | `build.sh` failed at the first `dotnet` call with `IOException ... 'NuGet-Migrations'`; works as root, not as UID 1000 even with a passwd entry or a fresh tmpfs `/tmp` | `docker/run.sh` runs as root and chowns created files back. |
| 12 | Interactive console showed nothing after `Starting kernel` | Kernel log: `printk: bootconsole [ec_imx6q0] disabled` when `tty0` registers; the serial console comes back only once the i.MX UART driver probes | Not a bug; `quiet` is part of Torizon's bootargs. For debugging only, `EXTRA_KARGS="ignore_loglevel earlycon=ec_imx6q,0x30880000 keep_bootcon"` builds a separate image. |

## Boot speed

Measured with the stock image, 4 cores, container capped at 3 GiB / 4 host CPUs (wall-clock time to the
login banner).

| # | Bottleneck | How it was found | Change | Effect |
|---|---|---|---|---|
| S1 | Busy-waits (U-Boot's autoboot countdown, kernel `udelay`/`mdelay` in drivers timing out on unmodeled peripherals) poll the ARM system counter. Each `CNTVCT/CNTPCT` read went through `ComparingTimer.Value` → `GetClockEntryInLockContext`, which runs a full `UpdateLimits` over every clock entry of the machine: ~0.5 µs per read, ~130x a plain instruction. | Per-line host/virtual timestamps of the console; PC samples every virtual second (cpu0 in `__delay`/`__delay_cycles` in nearly all samples during systemd); a bare Cortex-A53 loop benchmark: `mrs cntvct` loop 30.2 s vs `add` loop 3.7 s vs `mrs cntfrq` loop 7.7 s for 1 s of virtual time. `AdvanceImmediately` didn't help (cores spin, they aren't idle). | `ARM_GenericTimer.TimerUnit.Value`: counter computed from the clock source's elapsed virtual time, calibrated against the underlying timer when it is set (offset writes, reset). Compare interrupts are unchanged. | Counter loop 30.2 → 7.9 s. Boot to login banner 20.5 → 7.7 min (kernel start 110 → 18 s). |
| S2 | The eMMC driver ran in PIO mode (`mmc2: SDHCI controller ... using PIO`), and `sdhci-esdhc-imx` sets `SDHCI_QUIRK_PIO_NEEDS_DELAY`: `sdhci_transfer_pio` busy-waits 100 µs per 512-byte block. Every rootfs read during boot paid that. The uSDHC model implements DMA (U-Boot uses it), but reported `HOST_CTRL_CAP.DMASUP = 0`, so Linux didn't. | PC samples alone only showed `__delay`; a frame-pointer walk of cpu0's kernel stack (`scripts/backtrace.py`, a monitor helper that reads the frame records through the MMU) showed `__const_udelay < sdhci_irq` in nearly every busy sample. NXP `sdhci.c`: the only delay inlined there is the PIO one. | `NXP_uSDHC`: constructor option `dmaSupported` (default off, upstream behaviour unchanged), enabled for usdhc2/usdhc3 in the Verdin repl. | Boot to login banner 7.7 → 3.2 min; virtual time to the banner 83 → 67 s. No I/O errors. |
